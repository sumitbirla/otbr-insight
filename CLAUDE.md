# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OTBR Insight is a monitoring + management dashboard for OpenThread Border Router (OTBR). A single Go binary polls the OTBR REST API, normalizes its version-dependent responses, and serves an embedded web UI. It began read-only; it now also performs a bounded set of **writes** to OTBR (Thread network form/join/enable-disable/leave) over the REST API. No database beyond a small device-names file, and **no authentication** — the write endpoints assume a trusted LAN (a deliberate choice to match otbr-web's posture).

## Commands

```sh
make build          # local binary at dist/otbr-insight (CGO disabled, assets embedded)
make test           # go test ./...
make release        # cross-compile linux-amd64 + linux-arm64 into dist/
go test ./internal/otbr                      # single package
go test ./internal/otbr -run TestOverview    # single test
```

Run locally: `dist/otbr-insight --otbr-url http://127.0.0.1:8081 --listen :8088 --discovery-interval 5m`. `dist/otbr-insight -h` prints every flag with its effective default and the matching `OTBR_INSIGHT_*` variable (flags win over env vars). `Parse` and `Usage` share `defaults()` and `bindFlags`, so help can never drift from what the binary accepts; flags are parsed before env errors are reported so `-h` still works when a variable is malformed. See `internal/config/config.go`.

Go 1.26+, which is what `go.mod` declares. The MCP SDK's own floor is 1.25; `golang.org/x/net` (there for `dns/dnsmessage`) is what pushes it to 1.26, so `go mod tidy` puts the directive back if it is lowered. There is no frontend build step — `web/static/` (vanilla JS/CSS/HTML) is embedded via `go:embed` in `web/embed.go`, so a `make build` is needed to pick up frontend changes in the binary.

## Architecture

Data flows one direction, through two interfaces that keep the layers swappable:

```
OTBR REST API → internal/otbr (Client) → internal/service (Monitor) → internal/api → web/static
                 implements                implements
                 service.ThreadProvider    api.Snapshotter
```

- **`internal/model`** — the normalized, stable contract shared by all layers and serialized to the frontend. Provider-specific response shapes must not leak into these types (this is a stated invariant in the package). Pointer fields mean "OTBR version may omit this entirely."
- **`internal/otbr`** — the OTBR adapter and where all version-compat logic lives: node status from `/api/node` with legacy `/node` fallback, devices from `/api/devices`, topology from `/api/diagnostics`, plus optional extras scraped from the OTBR **web** service (`/get_properties`, `/available_network`), which lives on a *different port* from the REST API: when the configured OTBR URL uses port 8081, `NewClient` derives `legacyWebURL` by rewriting the host to port **80** (443 for https) and clearing the path (`client.go`), so these two are fetched from `http://<host>/…`, not `:8081`. Any other port leaves `legacyWebURL` nil and the extras are skipped. **otbr-web can be stopped independently of the REST API**, and then these two are simply gone: the REST API has no active-scan action (its `/api/actions` enum is `addThreadDeviceTask`, `getNetworkDiagnosticTask`, `resetNetworkDiagCounterTask`, `getEnergyScanTask`, `updateDeviceCollectionTask` — `getEnergyScanTask` is an 802.15.4 energy-detect scan reporting RSSI per channel, not network names or PAN IDs), so Nearby Networks cannot be reimplemented over REST. `ScanNetworks` therefore reports a transport failure as `status: "unavailable"` naming otbr-web, rather than surfacing a dial error, and `optionalStatusProperties` **clears its cache on failure** — keeping the last good values left a stale RCP version on screen indefinitely and made those fields flicker (absent on the poll that retried, present again from cache for the next minute). Capability probing (`knownEndpoints` + `Capabilities` in client.go) detects which endpoints a given OTBR build supports.
- **`internal/service`** — `Monitor` polls on independent tickers (overview at `--poll-interval`, devices+topology at 3× that with a 15s floor, capabilities every minute, mesh discovery at `--discovery-interval`), caches the last-valid snapshot behind a RWMutex, and marks data `stale` rather than dropping it when OTBR goes down. It also enriches data across sources: `mergeBorderRouter` injects/flags the local BR in the device list, and topology nodes get names/BR flags matched from the device inventory by extended address. Snapshot methods return deep copies of slices.
- **Signal history** — `internal/service/signal.go` keeps a per-device trail of the radio link, sampled in `refreshDevices` so it follows the poll cadence rather than how often somebody opens a device. Readings are folded into **one-minute buckets, 120 of them** (two hours): at a 5s poll that is 120 entries per device instead of ~1400, and each bucket carries mean/min/max RSSI so a dip survives the folding. **Absence is recorded, not skipped** — every known trail is advanced on every poll, so a device missing from the inventory leaves a visible gap, which is the only thing separating "quiet but healthy" from "gone"; a trail whose whole window is absence is dropped, and trails are capped at 256 devices. It is **memory only and deliberately so**: a sample every few seconds forever is not a disk write this app makes for a diagnostic aid, and the persistent state stays names plus one dataset backup. The cost is that a restart empties it, which the API states through `coveredSeconds` rather than implying a full window. Served at `GET /api/v1/devices/{ext}/signal` and as the `get_signal_history` MCP tool, both registered by type assertion. The MCP view **reduces the 120 buckets to at most 24 points** (`reduceSignal`) because handing a model two hours of minutes buries the shape in numbers; the reduction keeps each group's extremes, so a one-minute dip still reads as a dip. The frontend draws it as an inline SVG sparkline in the device popover and the expanded list row — a min-to-max band with the mean over it, gaps shaded — on a **fixed −100…−40 dBm scale** so two devices compare and a trail does not appear to improve because its own worst reading moved. It is fetched per device on demand (45s TTL, `state.signalTrails`), never folded into the poll, and one 404 retires the section rather than leaving every device reading "no trail yet".

- **`internal/api`** — thin `GET /api/v1/*` handlers over `Snapshotter` snapshots. Only `/api/v1/networks` calls through to OTBR live (on-demand active scan, can take seconds). Everything is wrapped in strict security headers. On read, `applyDeviceNames`/`applyTopologyNames` overlay user labels from the `NameStore` onto the snapshots as `customName`, keyed by extended address. **Write endpoints** (`registerControlRoutes`) call a `NetworkController` (the otbr `Client`) directly, then trigger a monitor `RefreshNow`: `GET /api/v1/network` (masked state+dataset), `GET /api/v1/network/credentials` (the **only** unmasked path), `POST /api/v1/network/{form,join}`, `POST /api/v1/network/join/tlv`, `POST /api/v1/network/restore`, `PUT /api/v1/network/state`, `DELETE /api/v1/network` (leave). Device naming adds `PUT`/`DELETE /api/v1/devices/{ext}/name`, `GET /api/v1/health` returns a bare status pair (503 when OTBR is unreachable) for probes, `GET /api/v1/history` serves OpenThread's event log on demand (overlaying user labels the same way the device list does), and `POST /api/v1/devices/{address}/ping` runs a reachability test from the border router — a POST because it makes the radio transmit, though it changes nothing. Both need the daemon socket and report clearly when it is absent. Four read routes are registered **conditionally, by type assertion**, and are documented with the subsystems they belong to rather than here: `GET /api/v1/channels` (energy scan), `GET /api/v1/fabrics` and `PUT`/`DELETE /api/v1/fabrics/{id}/name` (Matter fabrics), `GET /api/v1/devices/{ext}/signal` (signal history). `POST /api/v1/fabrics/identify` is the exception that registers unconditionally, since decoding a file needs no capability at all. These are all unauthenticated by design.
- **Firmware quirks to know** (observed on a Silicon Labs OTBR build): (1) the REST `Allow` header for `/node/state` and `/node/dataset/active` wrongly omits `PUT`, but `PUT` is the correct write method — state uses `PUT /node/state`, `application/json`, body `"enable"`/`"disable"` (a JSON string). (2) `/api/node` serves a **stale** cache after a dataset change (lingering `networkName`, `state`, `role`, `partitionId`, `routerCount`, `rlocAddress`), while `/node` stays fresh but omits some fields (OMR address). `Overview` fetches **both** and `mergeFreshNode` overlays `/node`'s live values onto the `/api/node` base (`client.go`). Note `/node` reports the role in its `state` field and has no `role`. The frontend shows a distinct "Network disabled" status (grey dot) when `status==online && state==disabled`, separate from "OTBR offline" (unreachable). (3) `/api/devices` and `/api/diagnostics` are **also** stale caches after a network change — they keep listing departed devices from the old network (every entry, even the border router, carries the old OMR prefix), and there is no fresh `/node`-style alternative. Since per-device data is unreliable, the monitor instead flags the whole inventory: `devicesMismatchNetwork` compares the authoritative `routerCount` (from `/node`) against the routers in the inventory, sets `DeviceInventory.NetworkMismatch`. **The flag is computed and served on `/api/v1/devices` but nothing in the UI reads it** — the "may include devices from a previous network" banner was removed by request, so ghosts are now shown without qualification. The practical mitigation is the periodic sweep in (4), which rebuilds the collection from live data; note that a sweep was only observed producing a clean list after an explicit `DELETE /api/devices`, so whether it evicts a departed device from an already-populated collection is unverified. If ghosts need surfacing again, `NetworkMismatch` is still there to drive it. (4) **OTBR never sweeps the mesh on its own.** `/api/devices` and `/api/diagnostics` are filled only when a client POSTs to `/api/actions`; left alone they freeze at the last sweep — observed frozen for 45 days, listing a departed router while omitting two live sleepy children. Sleepy end devices are *only* ever visible through a sweep, so a mesh of battery-powered devices reads as empty without one. **Two kinds of sweep are needed.** `updateDeviceCollectionTask` fills `/api/devices` but its records carry no `rloc16` and no `parent`; parent/child edges come only from each router's `childTable`, which is a separate `getNetworkDiagnosticTask` per router. Post only the first and every child floats unattached. `Client.RefreshMesh(ctx, routers)` posts both in one request (the array may mix action types), and `Monitor` calls it at startup and every `--discovery-interval` (default 5m, `0` disables), passing `knownRouters()` — the local BR from the overview plus any router in the last inventory. Hence `refreshOverview` runs *before* the startup sweep: without the BR's extended address the first sweep cannot ask for its childTable. Results land asynchronously and the normal device/topology polls pick them up. Schema traps, all answered with `422` and an empty `detail`: `data` must be a JSON **array**; all four of `maxAge`/`maxRetries`/`deviceCount`/`timeout` are required on the collection task despite each documenting a default; `timeout` is required on the diagnostic task too. The `destinationType` seen in stored action records is not a request field (the spec marks it TODO). And the diagnostic `timeout` must be generous — at 10s the task gives up in state `stopped` and writes no record; 60s completes. Discovery is exposed through the optional `service.DeviceDiscoverer` interface, and "unsupported" travels as a behavioural error (`DiscoveryUnsupported() bool`) so `internal/service` need not import `internal/otbr`.
- **`internal/otbr` network.go** — the dataset read/write layer. `ActiveDataset` reads `/node/dataset/active` and **masks `networkKey`/`pskc`** (reports only `hasNetworkKey`/`hasPskc`) so the polled read path never carries Thread credentials. `FormNetwork` generates a complete dataset (random key/pskc/extPanId/meshLocalPrefix) locally rather than relying on OTBR to fill blanks; `JoinNetwork` builds one from supplied creds. Both go through `applyDataset`, which must **disable → PUT active dataset → enable** (the active dataset can't be replaced while the interface is up). `LeaveNetwork` = disable + `DELETE` dataset (the REST-only stand-in; true `factoryreset` needs ot-ctl, which we deliberately don't use). **TLV interchange**: `ActiveDatasetTLV` exports the dataset as hex TLV (`text/plain` GET) — surfaced in the on-demand credential reveal for pasting into other border routers (Home Assistant's "Add dataset from TLV"); `JoinNetworkTLV` imports one via `PUT text/plain` through the shared `applyDatasetRaw`. Credentials (key/pskc/TLV) are served **only** from `GET /api/v1/network/credentials`, never the polled path, and never logged.
- **`internal/mcpserver`** — the Model Context Protocol endpoint, mounted by `api.Handler` at `/mcp` on the same listener and under the same no-auth LAN trust model as the REST API. Built on the official `modelcontextprotocol/go-sdk` (one of the module's two direct dependencies, the other being `golang.org/x/net` for mDNS) as **Streamable HTTP, stateless, JSON responses**: each tool call is one POST, so there is no session to idle out and no SSE stream to be cut by the HTTP server's 25s `WriteTimeout`; the handler also extends the write deadline per request so a 60s sleepy-device ping can complete. The SDK's localhost DNS-rebinding check is disabled because the README's nginx setup forwards the LAN Host to a loopback upstream, which that check refuses. Twelve tools: `get_network` (identity, border-router state, **device counts only** — quiet-over-10-minutes names included, never the device list, so the orientation call stays cheap — plus a `dataset` block and `backup` metadata), `list_devices` (with `role`/`query` filters), `get_topology` (nested router→children, router links, unattached children; routers ordered border router, leader, then provider order like the map), `scan_networks`, `scan_channels`, `list_fabrics`, `get_signal_history`, `get_capabilities`, `set_device_name`, `set_fabric_name`, `get_history` and `ping_device` — the last two are registered whenever the provider has the methods, which `otbr.Client` always does; without a socket they answer with the client's "needs the daemon socket" message rather than vanishing, the same as the REST routes. Results are shaped for reasoning: user labels resolved into `name`, parents given by name (resolved like the frontend's `topologyParent`: reported parent matched against router ids, else the router id in the child's RLOC16), ages as seconds, and the mesh-local address classified with `netip` against the overview prefix. `ping_device` accepts a name, extended address, RLOC16 or IPv6 literal and pings the mesh-local address (stable across roaming), falling back to OMR. **No network writes and no credentials** by design — those belong behind the UI confirm modal. The two exceptions are `set_device_name` and `set_fabric_name`, which write only to the local label file: identifying a device and then being unable to record what you learned was the gap that kept recurring. They are registered when the `Labels` value also satisfies `LabelWriter`, and a store with no data directory still registers them and answers with its own "naming is disabled" message rather than vanishing, like the socket-backed tools. An empty name is a **clear, not an error** — undoing a wrong label is the common case — and a fabric id must be the full 16 hex, since there is nothing to disambiguate a prefix against without a 3s mDNS browse. `get_network`'s `dataset` block deliberately carries only what the overview does not already say (present, interface state, active timestamp, `hasNetworkKey`/`hasPskc`), since repeating the name, channel and PAN ID would leave a reader guessing which copy is authoritative; a failed dataset read leaves the block absent rather than failing the orientation call every other tool depends on. `BackupReporter` reports the saved dataset's name and date through a **primitive signature supplied by an adapter in `internal/api`** (`backupMeta`), so this package still imports neither `internal/api` nor `internal/backup`, and the backup TLV — which carries the network key in plaintext — is not reachable from here at all. The package defines its own small interfaces (`Snapshots`, `Labels`, `LabelWriter`, `Pinger`, `HistoryProvider`, `CapabilityReporter`, `DatasetReporter`, `BackupReporter`) so it imports neither `internal/api` nor `internal/otbr`. The SDK logs every session at INFO and every stateless request is a session, so it is handed a logger filtered to WARN.
- **Channel noise (energy scan)** — `Client.EnergyScan` in `internal/otbr/energy.go` prefers the socket (`otctl.EnergyScan`, the `scan energy` table via `pipeTable`, keyed `ch`/`rssi`) and falls back to the REST action. The REST schema was found by trial against the Silicon Labs build, since the spec is silent: the body must be `application/vnd.api+json` (415 otherwise); `getEnergyScanTask` needs `destination` as the border router's **own extended address** (taken from `Overview`), `channelMask` as a **JSON array of channels** (an integer bitmask gets 422 with empty `detail`), and `count`/`period`/`scanDuration`/`timeout` all present. The POST echoes the created record with its `id`; poll `GET /api/actions/{id}` until `attributes.status == "completed"`, then read `relationships.result.data.id` and fetch `/api/diagnostics/{id}` — an `energyScanReport` whose `report[]` carries `maxRssi` as an **array** (one per count; the peak is kept). `repeatSweeps` runs the safe sweep repeatedly — `energyScanRun` (10s) with `energyScanPause` (300ms) between passes over the socket, `energyScanRESTSweeps` (3) identical verified requests over REST since each is ~6s of action polling — and combines per channel into `MaxRSSI` (loudest, what ranking uses) and `TypicalRSSI` (median); a failure after the first sweep ends the run with what was gathered. That is the answer to "a short listen is a snapshot", **not** a longer dwell. **Dwell time is fixed at the firmware default / 100 ms on REST and must stay that way**: a `scan energy 500` hung the EFR32 RCP (spinel timeout → `otbr-agent` aborts with `RadioSpinelNoResponse`; the LSB unit shows `active (exited)` so systemd does not restart it; a restart alone did not revive the RCP and only a USB power cycle did). Note also that the two paths measure differently — the CLI default dwell reported a −80 dBm floor where REST at 100 ms reported −95 — so channels are graded **relative to the quietest in the same scan** (≤3 dB quiet, >10 dB busy; `channelLevel` in both app.js and mcpserver) rather than against absolute thresholds — and the **current channel is graded and assessed on its typical (median) level, not its peak**: over 20+ sweeps its peak always catches one of this network's own frames (a child at −60), which no other channel can show, and ranking it by peak recommended leaving a channel that was at the floor 95% of the time. Candidates are still ranked by peak (a channel worth moving to must be clean at its worst), and the chart's bar height uses a fixed −105…−40 scale only so two measurements look alike. Served on demand at `GET /api/v1/channels` (registered only if the Snapshotter has `EnergyScan`, via type assertion), as the `scan_channels` MCP tool, and drawn in the "Channel noise" view with Wi-Fi 1/6/11 bands under channels 11–14/16–19/21–24 and a dot where the last nearby-network scan heard a Thread network.
- **`internal/backup`** — persists a single snapshot of the previous operational dataset (TLV hex, **network key in plaintext**) at `<data-dir>/dataset-backup.json`. The API's `snapshot` helper saves the current dataset before every destructive change (form/join/join-tlv/leave/restore) so `POST /api/v1/network/restore` can put it back; devices then auto-reconnect since credentials match. The TLV is used server-side only — `GET /api/v1/network` exposes just `backup` metadata (name + savedAt), never the TLV.
- **`internal/names`** — persists local state: a file-backed (`<data-dir>/names.json`, atomic write) map of extended address → user label. Fed by the two write endpoints `PUT`/`DELETE /api/v1/devices/{ext}/name`. Disabled (no-op, `ErrDisabled`) when no data dir is configured. Data dir resolves from `--data-dir`/`OTBR_INSIGHT_DATA_DIR`, else systemd's `STATE_DIRECTORY`, else the user config dir; the systemd unit sets `StateDirectory=otbr-insight` (`/var/lib/otbr-insight`).
- **Frontend structure** (`web/static/index.html`) — eight hash-routed views toggled by `syncNavigation` on `[data-view]`/`[data-nav]`: `home`, `manage` (setup), and under a TOOLS group `network` (nearby scan), `channels` (channel noise), `fabrics` (Matter fabrics), `report` (a device's decoded diagnostics export), `events` (the event log) and `help`. `report` is the one view with no server data behind it: it carries a header subtitle and an Upload button instead of an intro row, and `syncNavigation` hides the refresh button and freshness strip there, since nothing polls a file. The three on-demand scans were one combined view under a DISCOVER heading, with the channel and fabric panels stacked beneath the network scan; each is now its own view, so the sidebar names what the page can do and no scan is buried below another. Each carries a one-line intro with its action button, the description `<p>` taking the `data-term` so `decorateTerms` hangs the glossary `?` off it rather than needing a duplicate `<h2>`. `updateRefreshLabel` keys the freshness strip on the view (`scanViews`), not on which scan holds data, so a view never browsed reads as unscanned instead of borrowing the mesh poll's timestamp. One resolver, `activeView()`, maps hash to view for every caller, and legacy hashes fold into it: `#diagnostics` is the pre-rename name of the event log (it was called Diagnostics while it was the only tool; once the scans moved beside it under TOOLS the name oversold a view that is a timestamped record of what OpenThread saw). Its existence matters beyond routing — the poll's "don't clobber a non-home page title" guard used to list views by hand and went stale the moment `channels` and `fabrics` were added, so a poll on either replaced the heading with the network name; it now asks `activeView() === 'home'`. `home` is the landing and the default for any unknown hash; the pre-merge hashes `#overview`, `#devices` and `#topology` all fold into it so old bookmarks still resolve. On `manage`, **Form a network** and **Join a network** are `<details>` disclosures rather than two always-open forms: between them they are a dozen inputs, most of them hex, and on a router that already has a network none of them is the reason the page was opened. They default **open only when no dataset is present**, since setup is then the whole point of the page, and the decision is made once (`state.setupDisclosuresDecided`) because `/api/v1/network` is polled and re-deciding on every poll would shut a form mid-edit. `home` leads with the **mesh map** — a Map/List switch (`[data-device-mode]` toggling `[data-device-panel]`), then the topology stage or the device table — and puts the network identity and border-router/runtime details underneath in two `<details>` panels (`#networkDetailsDisclosure`, `#borderRouterDisclosure`) that stay collapsed until clicked. The page title is the live network name (`homeTitle()`, falling back to "Thread network" before the first poll) with channel and PAN ID beside it in `#titleMeta`, which is shown only on `home`. The map draws **one cluster per router** — the router with its own children wrapped beneath it — and packs clusters left to right, wrapping to a new band when the next will not fit; Clusters are ordered **local border router first, then the leader, then the provider's order** (`routerRank`, with a stable sort): the map previously inherited the API's router-id ordering, which put the one node the reader is certain of wherever its id happened to sort — id 28 of 4 routers landed it in the last band. `topologyGrid` is now used only for the unresolved-parent band. Column count comes from the scroll container's `clientWidth`; below 408px (two desktop columns plus margins) the layout switches to **compact metrics** — 12px margins and a 166px pitch instead of 24px/180px — because a phone's ~358px map area otherwise computed one column and stacked every cluster single file when two 154px cards fit in 344px. A **childless router** that would otherwise start a band alone is instead tucked into a spare top-row slot of the band's last cluster (`host`/`tucked` in the packing loop), with that cluster's router shifted from the centre to sit over its first child column — on a phone the IKEA router used to drop beneath the border router's two rows of children. Each cluster is capped at roughly half that (`clustersPerBand`) so two sit side by side rather than stacking into one tall column. This went through two earlier shapes: a single unwrapped row sized the stage from the largest layer (`largestLayer * 180 + 80`), so 36 children made it 6380px wide with 18% of the map on screen; wrapping that into one shared grid fixed the width but left a dense fan of long crossing child links. Clustering keeps every child link short and local. Horizontal scroll stays at 1.0x at any device count; the cost is height (36 children ≈ 1700px). The column count is part of the render-cache signature, so a window resize re-flows rather than hitting the cache. The detail views label the **mesh-local** address alongside the OMR one: it is reachable only inside the mesh (a browser on the LAN has no route to that prefix) but, unlike RLOC16, survives roaming, so it is the stable handle for `ot-ctl ping` while RLOC16s churn. `meshLocalAddress` picks it by matching the overview's mesh-local prefix. Each node card carries a second small line with the measured link and how long ago the device was heard (`-68 dBm · 5s ago`), shown only where a link was actually measured — the local border router has no link to itself, and a bare "just now" there would say nothing. The card height lives in `TOPOLOGY_NODE_HEIGHT`, which the edge geometry and the cluster layout both read; it must match the CSS `min-height` or edges detach from the boxes. Cluster width is capped to fit two per band **only when the natural layout does not fit** — capping unconditionally wrapped three children onto two rows with room to spare. Selecting a map node opens `#devicePopover`, a fixed non-modal panel in the same family as the term-help and rename popovers (dismissed by its ×, Escape, an outside click, re-clicking the node, switching to List, or navigating away) — it replaced a docked inspector column so the map gets the full width.
- **Hiding elements**: use the `.hidden` class (`display: none !important`), never the bare `hidden` attribute. Several components set `display` in their own rules, which beats the UA stylesheet's `[hidden] { display: none }` — an element can carry `hidden` and still render.
- **`web/static/app.js`** — single-page vanilla JS; polls the internal API only, never OTBR directly. The CSP is `'self'`-only with no inline allowance, so no inline `<script>`/`<style>`/event handlers in `index.html`. Display names prefer `customName` (see `deviceLabel`); the rename popover is a fixed element outside the polled device containers so a background refresh can't clobber an in-progress edit.

- **`internal/mdns` + `internal/matter`** — Matter fabric discovery over the LAN. `mdns.Browser` is a one-shot multicast DNS browser built on stdlib UDP and `golang.org/x/net/dns/dnsmessage` (the only non-MCP dependency; miekg/dns was ruled out earlier). It sends PTR queries from an **ephemeral port** — a "legacy unicast" query per RFC 6762 §6.7, so responders reply straight to that port and the host's own responder (avahi on the border router) keeps 5353 — plus a second socket joined to the group for responders that multicast anyway, repeating the query twice more over a 3s window because one query alone heard 20 of 24 nodes. IPv4 multicast only. Replies carry SRV/TXT/A/AAAA as additionals, so no per-instance follow-up is needed. **It browses subtypes, not just the service, and that is load-bearing.** A responder answers the broad `_matter._tcp` question at its own discretion, and one that stays quiet is simply absent — measured here, a node never answered it in any run, so the whole Matter fabric it was the sole member of was missing from every browse and the dashboard reported two fabrics where three existed. The first round therefore also asks the RFC 6763 §9 service-type enumeration (`_services._dns-sd._udp.local.`), which names every subtype on the link — for Matter one `_I<compressed-fabric-id>` per fabric — and later rounds query each of those beside the base service; the collector keys a PTR on what it points **at**, so base and subtype pointers to the same instance dedupe. **One question per datagram, never a multi-question packet**: a responder answers a multi-question query in a single response, and where that is a legacy unicast reply it must fit one packet, so asking four at once deepened the truncation and a browse from the border router fell from 22 nodes to 17. Split, it reads 25 nodes and all 3 fabrics, repeatably, against 27 from an unconstrained host. **On the border router itself the browse is incomplete by construction**: otbr-agent runs its own mDNS responder bound to `eth0:5353` (visible in `ss -ulnp` beside avahi) and its multicast replies never reach a local socket — a packet-level probe on the router saw every other host's multicast answers but only the router's own *legacy unicast* reply, which is one packet (1151 bytes) and silently drops the last Thread instances (consistently the same device). So `matter.Fabrics` merges each mesh device's SRP `Services` first, which is authoritative for what the mesh advertises, and lets mDNS fill in the LAN-only nodes; the two are deduplicated by fabric+node. `matter.Fabrics` groups instances by the `<compressed-fabric-id>-<node-id>` instance name and links a node to a mesh device when its SRV target is `<extaddr>.local.` — which is what the border router's advertising proxy publishes for Thread devices, so this joins to the inventory by extended address like everything else. Exposed as `Monitor.MatterFabrics` (optional `service.ServiceBrowser`, injected by `main`), `GET /api/v1/fabrics` (registered by type assertion, labels overlaid on mesh nodes), the `list_fabrics` MCP tool and the "Matter fabrics" view. A fabric is a controller's trust domain, not a Thread concept, so this is the one view that works with an empty mesh: Wi-Fi Matter devices and the controllers' hubs advertise too. Fabric IDs are hashes; the two practical tells are node numbering (Home Assistant's server counts up from 1, while Apple and Google assign random IDs) and the node's port (a controller's own operational advert uses a random port rather than 5540). Any host can browse; this is not tied to the border router.

  **Identifying a fabric from a controller's diagnostics export.** A browse only sees fabrics whose controllers are advertising, and it never learns their names — a compressed fabric ID is a hash. A Matter *device*, though, stores one root certificate per fabric it belongs to, and Home Assistant hands that whole attribute dump out per device (Settings → Devices → the device → Download diagnostics). `internal/matter/diagnostics.go` decodes it, with `internal/matter/tlv.go` as a minimal Matter TLV reader (core spec §A.7; little-endian, containers terminated rather than length-prefixed, tag width in the top three bits of the control byte). The difference between two attributes is the whole point: **`0/62/4` TrustedRootCertificates is not fabric-filtered**, so it lists every fabric the device is in including ones this controller cannot see, while **`0/62/1` Fabrics is**, so it describes only the producing controller's fabric — but with a label, vendor ID and the device's node ID in it. So one export *names* one fabric and *proves the existence* of the rest; naming them all needs one export per controller. The compressed fabric ID is derived per Matter spec §4.3.2.2: HKDF-SHA256 with the root public key **minus its leading `0x04` uncompressed-point marker** as key material, the fabric ID as eight big-endian bytes as salt, and `"CompressedFabric"` as info, 8 bytes out — `crypto/hkdf`, stdlib, no new dependency. **The two attributes are joined by root public key, not by elimination**, because measured against a real export Home Assistant's own root certificate carries *no* fabric ID in its subject (only an rcac-id), so its compressed ID cannot be derived from the certificate at all and comes from the Fabrics entry instead; matching on the key keeps that right when more than one root lacks a subject fabric ID. `server_info.compressed_fabric_id` is used **only as a cross-check**, and that check must compare like with like — it is a `uint64` and must be rendered as sixteen padded hex digits, not the trimmed `0x…` form `formatID` produces for fabric and node IDs, or it mismatches on every real export (it did, until a live run caught it). Served at `POST /api/v1/fabrics/identify`, registered **unconditionally** — pure decoding, no mDNS and no daemon socket, so it works on a host where `GET /api/v1/fabrics` does not exist. The upload is read once, decoded and discarded: it is a full attribute dump of somebody's device, so it is never stored, echoed back or logged, and no route reads it back. On the "Matter fabrics" view it merges into the cards: a browsed fabric the export names offers its label as a one-click suggestion (accepted rather than applied, since "Home" is that controller's word for itself), and a fabric in the certificates that **nothing advertised** gets its own dashed `NOT ADVERTISING` card — which is the diagnosis a browse alone cannot make, since it reports such a controller as simply not existing. Evidence accumulates across files in `state.fabricEvidence` for the session, and a later export that merely holds a root certificate never overwrites what an owning export knew. Fixtures here are **built, not captured** (`tlvBuilder` in the tests): a real certificate carries a live fabric's root public key, and the HKDF vector is pinned against an independent computation rather than against the implementation.



  **The full device report.** The same export carries far more than fabrics — 230 attributes for a door sensor — and `internal/matter/report.go` renders all of them, with `report_tables.go` holding the spec knowledge (cluster names, attribute labels, enums, units) and `report_certs.go` the certificate, access-control and group-key renderers. Three rules shape it. **Nothing is dropped**: an attribute no spec entry names still reaches the reader, grouped under its cluster number, because a curated report leaves no way to tell "not present" from "not understood" — `TestReportCoversEveryAttribute` pins that every input path appears as some entry's `Source`. **Units and enums are resolved server-side**, since rendering them raw is not merely terse but wrong: `BatPercentRemaining` is in *half* percent so a full battery reads 200%, `MeshLocalPrefix` is a 9-byte length-then-prefix octet string rather than an address, `ChannelPage0Mask` is a **bit string whose most significant bit is channel 0** so reading it as a big-endian integer reports the 802.15.4 band as channels 5–20, and `null` unmarshals into a nil slice without error so a null scalar renders as "none" and reads as an empty list — all four were live bugs caught by running real exports through, and all four are pinned by tests. The table also covers the **sensor clusters a device actually measures with** (temperature, humidity, air quality, the PM/VOC concentration family, on/off), because those are precisely where a raw number misleads: temperature and humidity are hundredths of a unit, so `2519` is 25.19 °C, and a concentration's unit lives in a *separate attribute* rather than in the value. The concentration clusters share one attribute layout, so they are generated from one map at init rather than written out per pollutant. **Certificates are decoded, not echoed**: `0/62/4`, `0/62/0` and `0/62/1` are summarised into subject IDs and validity dates through the same TLV reader the fabric identification uses. Attribute lookup falls back from `"0/29/0"` to `"*/29/0"` so Descriptor, Identify and the sensor clusters render on every endpoint, not just the root — without it a contact sensor's own state is a bare `true`. **Around 250 rows is a wall, so the report is banded and topped.** `report_highlights.go` lifts out the handful that answer "is this device all right" — battery, how it hears its parent, role, uptime, reboots, firmware, faults — as `Highlights` with a `Tone` the frontend colours. The tones are deliberately conservative and each is pinned by a test: the battery is graded on **the device's own `BatChargeLevel` and `BatReplacementNeeded` before the percentage**, since some chemistries read full until they collapse; the parent link is graded on **`LastRSSI`, never `AverageRssi`**, which real hardware reports tens of dB stronger than any actual measurement; **reboots are left uncoloured** because the count is since manufacture, so colouring it cries wolf on every device; and "no faults" is claimed **only when the device actually reported the fault lists as empty**, never from their absence. Each section carries a `Group` and an `Icon` **name** (not markup — the server ships data, and `REPORT_ICONS` in app.js owns the SVG), banded Overview → Thread and radio → Matter → What this device does → Everything else, with a non-root endpoint getting the fourth band because that is where the device's actual function lives. Sections are **sorted into band order last**, after the table and catch-all sections are appended: the frontend emits a heading whenever the group changes, so a band arriving in two runs drew its heading twice, which `TestReportBandsEachGroupContiguously` now prevents. Once a file is open the header names the device rather than saying "Device report": `EvidenceDevice.Name` is derived server-side as **NodeLabel, then ProductName** — the label a person gave the device through a controller beats the model name the manufacturer chose — and the subtitle switches from where-to-get-a-file to the vendor. Both Basic Information names are mandatory in the Matter spec so one is nearly always there, but `Name` is still allowed to be empty and the generic heading survives, because a **bridge** reports its own identity on endpoint 0 while each bridged device's name lives in Bridged Device Basic Information on its own endpoint, and Home Assistant redacts some strings in place (a redaction marker is not a name). The frontend makes no sense of any value: it draws sections as `<details>` cards, **all shut** — the highlights answer "is this device all right", so what is left is a reference to drill into, and an index of twenty titles with their counts reads better than eight open sections. That makes an **Expand all** control load-bearing rather than a convenience: a browser's find-in-page cannot reach text inside a closed `<details>`, so without it a 250-row reference document is unsearchable. Its label is kept honest by a `toggle` listener bound **once at startup in the capture phase** (`toggle` does not bubble, and a listener added per render would stack up on every import). It indents a sub-row when the server indents its label, and shows each entry's Matter attribute path so a reader can check it against the spec. Served in the same `POST /api/v1/fabrics/identify` response under `report`, and shown in its own **Device report** view under TOOLS — the fabrics view keeps its own import button because the two feed each other, and both open one file input parked beside the popovers rather than inside a `display:none` view. The report's freshness strip is stamped at import (`scanViews` maps `report` → `deviceReport`), since every counter in it froze when the file was downloaded; saying so is the one thing that separates it from the live views.

 **Fabric labels** reuse `internal/names` under a `fabric:<id>` key (`names.FabricKey`) — a fabric ID and an extended address are both sixteen hex digits, so the prefix is what keeps them apart — written by `PUT`/`DELETE /api/v1/fabrics/{id}/name` and overlaid on read as `MatterFabric.CustomName` and `AdvertisedService.FabricName` (both REST and MCP). The frontend's rename popover is shared: `RENAME_KINDS` in app.js selects the route and wording. The fabric card's tag reads **coverage, not membership**: every fabric a Thread device is paired with contains that device, so the original "THIS MESH" badge marked every fabric alike and read as though the fabric *were* the mesh (a fabric is a Matter controller's trust domain and spans Wi-Fi too). It now shows `ALL DEVICES`, `3 OF 4` or `LAN ONLY` against the union of Matter-commissioned mesh devices across all fabrics, and the line beneath names the missing ones — which is the diagnostically useful case, a device one controller never got. The summary note counts **distinct** mesh devices rather than summing per-fabric counts, since a device paired with two controllers is two nodes.

- **`tools/screenshots`** — regenerates the README images. Captures the **real** app (real assets, CSS and decoder) and substitutes only the data, for two reasons that are not convenience: a published mesh view carries network identity and every device's extended address, and a real energy scan takes the border router **off channel for ten seconds**. `shoot.mjs` drives headless Chrome over the DevTools Protocol using Node's global `WebSocket` — no npm tree, matching this repo's one-dependency posture. Two traps it encodes: `/json/new` accepts only **PUT** (a GET is refused with plain text that is not JSON), and the driver must **wait for the first poll** rather than sleeping, or the sidebar pill is caught reading "Connecting" and the shot looks like a broken instance. Scenes set the hash, call `syncNavigation()` and hand data to the view's render function — `app.js` is a classic script so its top-level functions are global. `sanitise.py` turns a real Matter diagnostics export into the committed fixture, replacing network identity, addresses, certificates, the controller node ID, the time zone and commissioning timestamps with documentation values while keeping vendor/product names, versions, counters and sensor readings, which are what make the image worth looking at. Prefer a cropped `HEIGHT` over `FULL=1`: the whole report is 2300 CSS px tall and renders as a sliver in a README.

- **`tools/matter-xref`** — a standalone Go command (not part of the server binary; `make build` only builds `./cmd/otbr-insight`) that matches Matter node IDs to mesh devices. A Matter QR code carries no Thread identity — only vendor/product IDs, a discriminator and the passcode — but the operational mDNS advert does: `_matter._tcp` instances are named `<compressed-fabric-id>-<node-id>` and their SRV target hostname **is the device's extended address**, which is exactly what this app keys devices on. It predates `internal/mdns`: it shells out to `dns-sd` or `avahi-browse` rather than browsing itself, and remains as a LAN-side check that needs no server.

- **`internal/otctl`** — the OpenThread CLI over otbr-agent's POSIX daemon UNIX socket (`/run/openthread-wpan0.sock` by default, `--otbr-socket`), the same channel `ot-ctl` and otbr-web use. It exists for capabilities the REST API has no action for, and for replacing ones REST does badly. So far: **active network discovery**; the **live device inventory and topology** (`Mesh`); the **runtime status fields** (`Status`) that otbr-web served from `/get_properties` — version strings, channel, TX power, EUI-64, link-local and mesh-local addresses (the mesh-local EID via `ipaddr mleid` — a first-ULA scan of `ipaddr` is only a fallback, because the OMR address is a ULA too and on real hardware it is listed *before* the EID, which put the OMR address in the mesh-local field), cached for `statusTTL` since they are near-static, with `WPANService` *derived* from the role because the CLI has no direct equivalent; **reachability testing** (`Ping`), whose timeout must accommodate a sleepy device — measured replies take 2.5-5s and the CLI's one-second default reports a live device as 100% lost; and **event history** (`History`), OpenThread's own recorder, which is the only source for *when* something happened — REST reports current state only, so a departed device is simply absent with no record of when or at what signal. `Mesh` reads `meshdiag topology` for the router set and inter-router links, then `meshdiag childtable <rloc16>` per router — including our own, which works — for children with `ext-addr`, RSSI, margin and frame/message error rates. It answers from the mesh at the moment it is asked, so it has **no cache to go stale**: departed devices vanish at once and sleepy children need no sweep. `Mesh` splits its work by cost: the over-the-air `meshdiag` queries are cached for `meshStructureTTL` while ages and RSSI are re-read from the local `neighbor table` on every call, so "last seen" tracks reality without extra radio traffic. That is also why `Client.FastDevices` reports true when a live reader is present — `Monitor` then polls devices at the overview cadence instead of the 15s floor, which is what previously made "last seen" lag by up to a full interval. It is injected as an optional `otbr.MeshReader`, preferred by `Devices` and `Topology`, with one reading cached for `meshSnapshotTTL` (2s) so a poll queries each router once rather than twice. A failed read falls back to the REST collections and **logs the transition** (both directions) — otherwise the degradation is invisible in the API response. While the live reader works, `RefreshMesh` skips posting discovery actions entirely: they only refresh caches nothing reads, and each sweep costs airtime. **Error rates are a rolling EWMA, not a total.** `SuccessRateTracker::AddSample` computes `rate = (old*(n-1) + sample + n/2) / n` with the default weight `n = 64`, so the figure reflects roughly the last ~64 transmissions to that neighbour — it is neither "since attach" nor "since boot", and the wall-clock span it covers depends entirely on traffic. Also note the value comes from two different commands with different formatting: `meshdiag childtable` writes `30.97%` for children, `neighbor linkquality` writes `0.09 %` (with a space) and is the **only** source for a *router* neighbour's rates — children are all `meshdiag childtable` covers, which is why routers reported no retry data at all until it was added. Note `meshdiag` reports a dB link margin while the UI draws a 0–3 LQI, so `qualityFromMargin` maps it using OpenThread's own thresholds (>20 dB → 3, >10 → 2, >2 → 1). **Addresses need three sources.** `meshdiag childtable` carries no IPv6 at all, so children get theirs from `meshdiag childip6 <rloc16>`; routers appear in no childtable, so theirs come from `srp server host`, whose hostnames are extended addresses (`0102030405060708.default.service.arpa.`) and therefore join directly to how this app keys devices — skipping `deleted: true` entries, which are unexpired leases rather than live devices. The local border router registers nothing with its own SRP server, so its addresses come from `ipaddr` via `localAddresses`, which drops the link-local one and every `…:0:ff:fe00:xxxx` anycast/routing locator — those encode an RLOC16 or ALOC and churn with the node's role — leaving the mesh-local EID and the OMR address. Its OMR is also filled from the overview by `mergeBorderRouter` as a fallback. A child holds both a mesh-local and an OMR address and both are ULAs, so `pickOMR` classifies them against the prefix from `br omrprefix` rather than guessing by shape. One more live-data hazard: after roaming, **both the old and new parent list a child** until the stale entry ages out, so children are deduplicated by extended address. **Router link metrics come from elsewhere again**: `meshdiag topology` gives only an adjacency and its quality bucket, so `routerMetrics` reads `router table` (LQ in/out, path cost) and `neighbor table` (average and last RSSI) — both local, no radio cost — and applies them to router nodes and router links. A router's own row reads LQ 0 / cost 0 about itself, so the local router is excluded: rendering that would look like a dead link rather than "not applicable". Table parsing goes through `pipeTable`, which keys cells by header name; column sets vary by command and firmware, which is what made the missing `J` column in `discover` a non-event. otbr-web's `/available_network` is a JSON wrapper around the CLI scan table (`src/web/web-service/ot_client.cpp` dials the socket and `sscanf`s the output), and the REST `/api/actions` enum offers only `getEnergyScanTask`, an 802.15.4 energy-detect scan reporting RSSI per channel rather than the networks on air. `Execute` writes one command and reads until `Done`, turning `Error N: …` into a Go error and refusing a reply that never terminates; embedded newlines are rejected so a caller cannot smuggle a second command. **Discovery is probabilistic**: a pass sends one request per channel and listens briefly, and a neighbour's router answers after a random delay, so measured on live hardware a single `discover` heard a given neighbour in about half of runs (Nest 2/5, another 1/5) and the list changed on every press. `otbr.Client.ScanNetworks` therefore runs `networkScanPasses` (3) passes through `mergedDiscovery` and unions them by identity, reporting `Passes` so the UI can say so. **Scans make the border router deaf to its own children.** Measured: whole-band `discover` = 4.9 s continuously off channel 25, `discover <ch>` = 0.3 s, one `scan energy` sweep = 0.1 s. Three whole-band passes (15 s away) made every sleepy child fail its polls, re-attach, and — the border router still being away — land on the IKEA router; the tell-tale in the event log is *pairs of children re-attaching in the same second*. `otctl.ScanNetworks` therefore issues `discover <channel>` per channel with `discoveryChannelPause` (150 ms) at home between them (falling back to whole-band `discover` if the first channel is rejected, then `scan`), which makes a pass ~7.5 s but never more than 0.3 s away at a stretch; the `/api/v1/networks` route extends its write deadline because three passes now take ~25 s. The energy scan already had this shape (100 ms sweep, 300 ms pause). Also measured: **the posix daemon holds one session at a time and a new connection displaces the old one mid-command** — a raw `discover` on a second connection received the header and then nothing, no rows and no `Done`, while the app polled, and completed once the app was stopped; the app's own commands are safe because `Execute` serialises them under one mutex, but a hand-run `ot-ctl discover` alongside the running app heard nothing in 4 of 5 runs. `ScanNetworks` prefers `discover` and falls back to `scan` on firmware without it — so this returns *more* than otbr-web did, whose results carried no name or extended PAN ID. **Verified against OPENTHREAD/8fbe09e**: `discover` emits seven columns — `Network Name | Extended PAN | PAN | MAC Address | Ch | dBm | LQI` — with **no joinable (`J`) column** despite the upstream CLI docs, CRLF line endings, and the *same network repeated once per responding beacon*, so exact duplicates are collapsed. The parser keys on the header row rather than column positions, which is why the missing `J` needed no change.

  **Advertised services (SRP).** `internal/otctl/srp.go` reads the border router's SRP (Service Registration Protocol) registry — `srp server host` for addresses and leases, `srp server service` for what each host advertises — and `applyRegistration` in `mesh.go` attaches it to each device as `Registration` (lease, lapsed, commissionable) and `Services` (instance, type, port, decoded TXT, and for `_matter._tcp` the fabric and node ID from the `<fabric>-<node>` instance name). It is the only place a Thread device says what it is, and the only way to tell "on the mesh but invisible to controllers" from "not on the mesh". Both reads are local, no radio cost. Traps: a host `deleted: true` is an unexpired key lease, kept and flagged `Lapsed` with its addresses dropped so a ping is not aimed at stale ones; a **deleted service prints no `host:` line** so it cannot be attributed and is dropped; TXT values are hex on the wire (`SII=3135383030` is `"15800"`); a live `_matterc._udp` is the commissioning advert a Matter device withdraws once paired, so it means "in pairing mode now" — surfaced as a warning-coloured `PAIRING` badge on the map node and the list row (`pairingService`/`pairingBadge` in app.js) and as a `Pairing mode` row naming the TXT discriminator, which is how a controller tells two devices pairing at once apart. **This can only ever show a window opened by a device already on the mesh** (adding a second controller): initial commissioning runs over Bluetooth before the device joins Thread, so a factory-fresh device registers nothing with SRP and cannot appear. The badge's negative case is verified live (no device open, no badge) and the positive path is covered by fixture only, since putting real hardware into pairing mode was not part of the session; the assumption it rests on is that a live `_matterc._udp` record prints a `host:` line, as every live `_matter._tcp` one does — without it the record cannot be attributed to a device and is dropped, since a commissioning instance name is random rather than `<fabric>-<node>`. The popover shows rows only when some device in the inventory carries a registration, so the REST fallback (which has none) does not read as "nobody registered". The local border router registers nothing with its own server.

  It is wired in as an **optional** `otbr.NetworkScanner`, injected by `main` and preferred over the otbr-web endpoint when the socket exists; `internal/otbr` never imports it. A present-but-failing socket reports the failure rather than silently falling back, so the two sources stay distinguishable in the UI. **This is the one part of otbr-insight that must run on the border router** — a UNIX socket is not reachable over a network — so everything else stays REST-only and host-agnostic. Deployment: the socket is **mode 0755 root:root**, and since `connect()` needs write access **only root can open it** — measured, not assumed (a non-root process gets `connect: permission denied`). So `DynamicUser=yes` cannot scan; the unit documents running as root, granting a group, or accepting no scanning. It also needs `ReadWritePaths=-/run/openthread-wpan0.sock` under `ProtectSystem=strict`. Because `Available()` is only a stat, an unopenable socket would otherwise shadow a working otbr-web, so an error reporting `SocketUnavailable()` falls through to otbr-web while any other daemon error is surfaced — "could not reach the source" and "the source answered badly" are deliberately different. See `deploy/otbr-insight.service`.

A future `ot-ctl` provider is the intended extension point: implement `service.ThreadProvider` without touching `internal/model` or the frontend.

## Conventions

- Writes are **bounded and REST-only**, with one deliberate exception. The app talks to OTBR over the `:8081` REST API for everything it can, and never shells out to a binary. `internal/otctl` speaks the daemon socket protocol directly (no subprocess) **only** for active scanning, because REST has no action for it; it is optional and absent-socket means absent-capability. Do not widen it without a reason of the same kind: every capability added there costs the property that otbr-insight can run anywhere and point at any border router. PSKd commissioning and factory reset remain out of scope.
- **Never expose Thread credentials on a read path.** The network key and PSKc are masked in `ActiveDataset` and must stay masked; the frontend polls `/api/v1/network` continuously.
- Any new destructive/network-changing operation must go through the frontend confirm modal (`openConfirm`) — never fire it on a single click.
- Tests use `httptest` servers returning canned OTBR payloads (see `internal/otbr/client_test.go`); new normalization paths should get a fixture for each OTBR response variant they handle.
- **Sanitise fixtures at the point of capture, not at review.** Test payloads and the sample CLI output in doc comments are pasted from live hardware, so the moment to replace real values is when they are captured — by the time anything is being published it is already too late to be sure. This is not hypothetical: a pre-publication audit found the **live network key and PSKc** in `internal/otbr/network_test.go`, and that same key used as the `placeholder` on the Network key input in `index.html`, where it shipped inside the binary. Scrub credentials (network key, PSKc), network identity (name, PAN ID, extended PAN ID, mesh-local and OMR prefixes) and every hardware address — device extended addresses are effectively MACs, and so are the RCP's EUI-64 and the border-agent ID. Note also that a `discover` fixture captures **neighbouring networks**, whose names and extended PAN IDs are someone else's to publish rather than ours. **A screenshot is a capture too**, and so is a Matter diagnostics export: a published view of a live mesh carries the network name, PAN IDs and every device's extended address, and an export adds the device's certificates, its IPv6 addresses, the controller's node ID, and — less obviously — the time zone and commissioning timestamps, which are a location hint and a when-did-somebody-set-this-up signal. `tools/screenshots/sanitise.py` exists for exactly that, and the screenshot scenes substitute data rather than photographing the real network. Reuse the documentation values already in the tree (`00112233445566778899aabbccddeeff`, `1122334455667788`, `fdde:ad00:beef`, `fd11:2233:4455`, sequential `0102030405060708`-style addresses), keeping the same length and shape so header-keyed table parsing and prefix matching still exercise what they did. Two traps that a search for the full secret will miss: a PAN ID also appears in **decimal** (`0xa1b2` is `41394`), and an assertion may check an **8-character prefix** of a key rather than the whole value.
- Topology child nodes are identified by **extended address** whenever the diagnostic `children` TLV (TLV 30) reports one: `childTable` carries only a child ID, but `children` adds `extAddress` and the real `rloc16`, so `decodeTopology` merges the two by child ID. That extended address is what matches the device inventory, so user-assigned names reach the map and a child can be renamed from it. Firmware that omits `children` falls back to the old derived id (`<parent>/child/<n>`, RLOC16 computed as parent+childID), which is stable only within one topology snapshot — keep that fallback working.
