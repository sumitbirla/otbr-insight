# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OTBR Insight is a monitoring + management dashboard for OpenThread Border Router (OTBR). A single Go binary polls the OTBR REST API, normalizes its version-dependent responses, and serves an embedded web UI. It began read-only; it now also performs a bounded set of **writes** to OTBR (Thread network form/join/enable-disable/leave) over the REST API. No database beyond a small device-names file, and **no authentication** — the write endpoints assume a trusted LAN (a deliberate choice to match otbr-web's posture).

## Commands

```sh
make build          # local binary at dist/otbr-insight (CGO disabled, assets embedded)
make test           # go test ./...
make release        # cross-compile linux-amd64 + linux-arm64 into dist/
go test ./internal/otbr                      # single package
go test ./internal/otbr -run TestOverview    # single test
```

Run locally: `dist/otbr-insight --otbr-url http://127.0.0.1:8081 --listen :8088 --discovery-interval 5m`. `dist/otbr-insight -h` prints every flag with its effective default and the matching `OTBR_INSIGHT_*` variable (flags win over env vars). `Parse` and `Usage` share `defaults()` and `bindFlags`, so help can never drift from what the binary accepts; flags are parsed before env errors are reported so `-h` still works when a variable is malformed. See `internal/config/config.go`.

Go 1.25+ (the MCP SDK's floor). There is no frontend build step — `web/static/` (vanilla JS/CSS/HTML) is embedded via `go:embed` in `web/embed.go`, so a `make build` is needed to pick up frontend changes in the binary.

## Architecture

Data flows one direction, through two interfaces that keep the layers swappable:

```
OTBR REST API → internal/otbr (Client) → internal/service (Monitor) → internal/api → web/static
                 implements                implements
                 service.ThreadProvider    api.Snapshotter
```

- **`internal/model`** — the normalized, stable contract shared by all layers and serialized to the frontend. Provider-specific response shapes must not leak into these types (this is a stated invariant in the package). Pointer fields mean "OTBR version may omit this entirely."
- **`internal/otbr`** — the OTBR adapter and where all version-compat logic lives: node status from `/api/node` with legacy `/node` fallback, devices from `/api/devices`, topology from `/api/diagnostics`, plus optional extras scraped from the OTBR **web** service (`/get_properties`, `/available_network`), which lives on a *different port* from the REST API: when the configured OTBR URL uses port 8081, `NewClient` derives `legacyWebURL` by rewriting the host to port **80** (443 for https) and clearing the path (`client.go`), so these two are fetched from `http://<host>/…`, not `:8081`. Any other port leaves `legacyWebURL` nil and the extras are skipped. **otbr-web can be stopped independently of the REST API**, and then these two are simply gone: the REST API has no active-scan action (its `/api/actions` enum is `addThreadDeviceTask`, `getNetworkDiagnosticTask`, `resetNetworkDiagCounterTask`, `getEnergyScanTask`, `updateDeviceCollectionTask` — `getEnergyScanTask` is an 802.15.4 energy-detect scan reporting RSSI per channel, not network names or PAN IDs), so Nearby Networks cannot be reimplemented over REST. `ScanNetworks` therefore reports a transport failure as `status: "unavailable"` naming otbr-web, rather than surfacing a dial error, and `optionalStatusProperties` **clears its cache on failure** — keeping the last good values left a stale RCP version on screen indefinitely and made those fields flicker (absent on the poll that retried, present again from cache for the next minute). Capability probing (`knownEndpoints` + `Capabilities` in client.go) detects which endpoints a given OTBR build supports.
- **`internal/service`** — `Monitor` polls on independent tickers (overview at `--poll-interval`, devices+topology at 3× that with a 15s floor, capabilities every minute, mesh discovery at `--discovery-interval`), caches the last-valid snapshot behind a RWMutex, and marks data `stale` rather than dropping it when OTBR goes down. It also enriches data across sources: `mergeBorderRouter` injects/flags the local BR in the device list, and topology nodes get names/BR flags matched from the device inventory by extended address. Snapshot methods return deep copies of slices.
- **`internal/api`** — thin `GET /api/v1/*` handlers over `Snapshotter` snapshots. Only `/api/v1/networks` calls through to OTBR live (on-demand active scan, can take seconds). Everything is wrapped in strict security headers. On read, `applyDeviceNames`/`applyTopologyNames` overlay user labels from the `NameStore` onto the snapshots as `customName`, keyed by extended address. **Write endpoints** (`registerControlRoutes`) call a `NetworkController` (the otbr `Client`) directly, then trigger a monitor `RefreshNow`: `GET /api/v1/network` (masked state+dataset), `GET /api/v1/network/credentials` (the **only** unmasked path), `POST /api/v1/network/{form,join}`, `POST /api/v1/network/join/tlv`, `POST /api/v1/network/restore`, `PUT /api/v1/network/state`, `DELETE /api/v1/network` (leave). Device naming adds `PUT`/`DELETE /api/v1/devices/{ext}/name`, `GET /api/v1/health` returns a bare status pair (503 when OTBR is unreachable) for probes, `GET /api/v1/history` serves OpenThread's event log on demand (overlaying user labels the same way the device list does), and `POST /api/v1/devices/{address}/ping` runs a reachability test from the border router — a POST because it makes the radio transmit, though it changes nothing. Both need the daemon socket and report clearly when it is absent. These are all unauthenticated by design.
- **Firmware quirks to know** (observed on a Silicon Labs OTBR build): (1) the REST `Allow` header for `/node/state` and `/node/dataset/active` wrongly omits `PUT`, but `PUT` is the correct write method — state uses `PUT /node/state`, `application/json`, body `"enable"`/`"disable"` (a JSON string). (2) `/api/node` serves a **stale** cache after a dataset change (lingering `networkName`, `state`, `role`, `partitionId`, `routerCount`, `rlocAddress`), while `/node` stays fresh but omits some fields (OMR address). `Overview` fetches **both** and `mergeFreshNode` overlays `/node`'s live values onto the `/api/node` base (`client.go`). Note `/node` reports the role in its `state` field and has no `role`. The frontend shows a distinct "Network disabled" status (grey dot) when `status==online && state==disabled`, separate from "OTBR offline" (unreachable). (3) `/api/devices` and `/api/diagnostics` are **also** stale caches after a network change — they keep listing departed devices from the old network (every entry, even the border router, carries the old OMR prefix), and there is no fresh `/node`-style alternative. Since per-device data is unreliable, the monitor instead flags the whole inventory: `devicesMismatchNetwork` compares the authoritative `routerCount` (from `/node`) against the routers in the inventory, sets `DeviceInventory.NetworkMismatch`. **The flag is computed and served on `/api/v1/devices` but nothing in the UI reads it** — the "may include devices from a previous network" banner was removed by request, so ghosts are now shown without qualification. The practical mitigation is the periodic sweep in (4), which rebuilds the collection from live data; note that a sweep was only observed producing a clean list after an explicit `DELETE /api/devices`, so whether it evicts a departed device from an already-populated collection is unverified. If ghosts need surfacing again, `NetworkMismatch` is still there to drive it. (4) **OTBR never sweeps the mesh on its own.** `/api/devices` and `/api/diagnostics` are filled only when a client POSTs to `/api/actions`; left alone they freeze at the last sweep — observed frozen for 45 days, listing a departed router while omitting two live sleepy children. Sleepy end devices are *only* ever visible through a sweep, so a mesh of battery-powered devices reads as empty without one. **Two kinds of sweep are needed.** `updateDeviceCollectionTask` fills `/api/devices` but its records carry no `rloc16` and no `parent`; parent/child edges come only from each router's `childTable`, which is a separate `getNetworkDiagnosticTask` per router. Post only the first and every child floats unattached. `Client.RefreshMesh(ctx, routers)` posts both in one request (the array may mix action types), and `Monitor` calls it at startup and every `--discovery-interval` (default 5m, `0` disables), passing `knownRouters()` — the local BR from the overview plus any router in the last inventory. Hence `refreshOverview` runs *before* the startup sweep: without the BR's extended address the first sweep cannot ask for its childTable. Results land asynchronously and the normal device/topology polls pick them up. Schema traps, all answered with `422` and an empty `detail`: `data` must be a JSON **array**; all four of `maxAge`/`maxRetries`/`deviceCount`/`timeout` are required on the collection task despite each documenting a default; `timeout` is required on the diagnostic task too. The `destinationType` seen in stored action records is not a request field (the spec marks it TODO). And the diagnostic `timeout` must be generous — at 10s the task gives up in state `stopped` and writes no record; 60s completes. Discovery is exposed through the optional `service.DeviceDiscoverer` interface, and "unsupported" travels as a behavioural error (`DiscoveryUnsupported() bool`) so `internal/service` need not import `internal/otbr`.
- **`internal/otbr` network.go** — the dataset read/write layer. `ActiveDataset` reads `/node/dataset/active` and **masks `networkKey`/`pskc`** (reports only `hasNetworkKey`/`hasPskc`) so the polled read path never carries Thread credentials. `FormNetwork` generates a complete dataset (random key/pskc/extPanId/meshLocalPrefix) locally rather than relying on OTBR to fill blanks; `JoinNetwork` builds one from supplied creds. Both go through `applyDataset`, which must **disable → PUT active dataset → enable** (the active dataset can't be replaced while the interface is up). `LeaveNetwork` = disable + `DELETE` dataset (the REST-only stand-in; true `factoryreset` needs ot-ctl, which we deliberately don't use). **TLV interchange**: `ActiveDatasetTLV` exports the dataset as hex TLV (`text/plain` GET) — surfaced in the on-demand credential reveal for pasting into other border routers (Home Assistant's "Add dataset from TLV"); `JoinNetworkTLV` imports one via `PUT text/plain` through the shared `applyDatasetRaw`. Credentials (key/pskc/TLV) are served **only** from `GET /api/v1/network/credentials`, never the polled path, and never logged.
- **`internal/mcpserver`** — the Model Context Protocol endpoint, mounted by `api.Handler` at `/mcp` on the same listener and under the same no-auth LAN trust model as the REST API. Built on the official `modelcontextprotocol/go-sdk` (the module's only dependency) as **Streamable HTTP, stateless, JSON responses**: each tool call is one POST, so there is no session to idle out and no SSE stream to be cut by the HTTP server's 25s `WriteTimeout`; the handler also extends the write deadline per request so a 60s sleepy-device ping can complete. The SDK's localhost DNS-rebinding check is disabled because the README's nginx setup forwards the LAN Host to a loopback upstream, which that check refuses. Six tools: `get_network` (identity, border-router state, and **device counts only** — quiet-over-10-minutes names included, never the device list, so the orientation call stays cheap), `list_devices` (with `role`/`query` filters), `get_topology` (nested router→children, router links, unattached children; routers ordered border router, leader, then provider order like the map), `scan_networks`, `get_history` and `ping_device` — the last two are registered whenever the provider has the methods, which `otbr.Client` always does; without a socket they answer with the client's "needs the daemon socket" message rather than vanishing, the same as the REST routes. Results are shaped for reasoning: user labels resolved into `name`, parents given by name (resolved like the frontend's `topologyParent`: reported parent matched against router ids, else the router id in the child's RLOC16), ages as seconds, and the mesh-local address classified with `netip` against the overview prefix. `ping_device` accepts a name, extended address, RLOC16 or IPv6 literal and pings the mesh-local address (stable across roaming), falling back to OMR. **No network writes and no credentials** by design — the writes belong behind the UI confirm modal. The package defines its own small interfaces (`Snapshots`, `Labels`, `Pinger`, `HistoryProvider`) so it imports neither `internal/api` nor `internal/otbr`. The SDK logs every session at INFO and every stateless request is a session, so it is handed a logger filtered to WARN.
- **Channel noise (energy scan)** — `Client.EnergyScan` in `internal/otbr/energy.go` prefers the socket (`otctl.EnergyScan`, the `scan energy` table via `pipeTable`, keyed `ch`/`rssi`) and falls back to the REST action. The REST schema was found by trial against the Silicon Labs build, since the spec is silent: the body must be `application/vnd.api+json` (415 otherwise); `getEnergyScanTask` needs `destination` as the border router's **own extended address** (taken from `Overview`), `channelMask` as a **JSON array of channels** (an integer bitmask gets 422 with empty `detail`), and `count`/`period`/`scanDuration`/`timeout` all present. The POST echoes the created record with its `id`; poll `GET /api/actions/{id}` until `attributes.status == "completed"`, then read `relationships.result.data.id` and fetch `/api/diagnostics/{id}` — an `energyScanReport` whose `report[]` carries `maxRssi` as an **array** (one per count; the peak is kept). `repeatSweeps` runs the safe sweep repeatedly — `energyScanRun` (10s) with `energyScanPause` (300ms) between passes over the socket, `energyScanRESTSweeps` (3) identical verified requests over REST since each is ~6s of action polling — and combines per channel into `MaxRSSI` (loudest, what ranking uses) and `TypicalRSSI` (median); a failure after the first sweep ends the run with what was gathered. That is the answer to "a short listen is a snapshot", **not** a longer dwell. **Dwell time is fixed at the firmware default / 100 ms on REST and must stay that way**: a `scan energy 500` hung the EFR32 RCP (spinel timeout → `otbr-agent` aborts with `RadioSpinelNoResponse`; the LSB unit shows `active (exited)` so systemd does not restart it; a restart alone did not revive the RCP and only a USB power cycle did). Note also that the two paths measure differently — the CLI default dwell reported a −80 dBm floor where REST at 100 ms reported −95 — so channels are graded **relative to the quietest in the same scan** (≤3 dB quiet, >10 dB busy; `channelLevel` in both app.js and mcpserver) rather than against absolute thresholds — and the **current channel is graded and assessed on its typical (median) level, not its peak**: over 20+ sweeps its peak always catches one of this network's own frames (a child at −60), which no other channel can show, and ranking it by peak recommended leaving a channel that was at the floor 95% of the time. Candidates are still ranked by peak (a channel worth moving to must be clean at its worst), and the chart's bar height uses a fixed −105…−40 scale only so two measurements look alike. Served on demand at `GET /api/v1/channels` (registered only if the Snapshotter has `EnergyScan`, via type assertion), as the `scan_channels` MCP tool, and drawn in the network view's "Channel noise" panel with Wi-Fi 1/6/11 bands under channels 11–14/16–19/21–24 and a dot where the last nearby-network scan heard a Thread network.
- **`internal/backup`** — persists a single snapshot of the previous operational dataset (TLV hex, **network key in plaintext**) at `<data-dir>/dataset-backup.json`. The API's `snapshot` helper saves the current dataset before every destructive change (form/join/join-tlv/leave/restore) so `POST /api/v1/network/restore` can put it back; devices then auto-reconnect since credentials match. The TLV is used server-side only — `GET /api/v1/network` exposes just `backup` metadata (name + savedAt), never the TLV.
- **`internal/names`** — persists local state: a file-backed (`<data-dir>/names.json`, atomic write) map of extended address → user label. Fed by the two write endpoints `PUT`/`DELETE /api/v1/devices/{ext}/name`. Disabled (no-op, `ErrDisabled`) when no data dir is configured. Data dir resolves from `--data-dir`/`OTBR_INSIGHT_DATA_DIR`, else systemd's `STATE_DIRECTORY`, else the user config dir; the systemd unit sets `StateDirectory=otbr-insight` (`/var/lib/otbr-insight`).
- **Frontend structure** (`web/static/index.html`) — four hash-routed views toggled by `syncNavigation` on `[data-view]`/`[data-nav]`: `home`, `network` (nearby scan), `help`, `manage` (setup). `home` is the landing and the default for any unknown hash; the pre-merge hashes `#overview`, `#devices` and `#topology` all fold into it so old bookmarks still resolve. `home` leads with the **mesh map** — a Map/List switch (`[data-device-mode]` toggling `[data-device-panel]`), then the topology stage or the device table — and puts the network identity and border-router/runtime details underneath in two `<details>` panels (`#networkDetailsDisclosure`, `#borderRouterDisclosure`) that stay collapsed until clicked. The page title is the live network name (`homeTitle()`, falling back to "Thread network" before the first poll) with channel and PAN ID beside it in `#titleMeta`, which is shown only on `home`. The map draws **one cluster per router** — the router with its own children wrapped beneath it — and packs clusters left to right, wrapping to a new band when the next will not fit; Clusters are ordered **local border router first, then the leader, then the provider's order** (`routerRank`, with a stable sort): the map previously inherited the API's router-id ordering, which put the one node the reader is certain of wherever its id happened to sort — id 28 of 4 routers landed it in the last band. `topologyGrid` is now used only for the unresolved-parent band. Column count comes from the scroll container's `clientWidth`, and each cluster is capped at roughly half that (`clustersPerBand`) so two sit side by side rather than stacking into one tall column. This went through two earlier shapes: a single unwrapped row sized the stage from the largest layer (`largestLayer * 180 + 80`), so 36 children made it 6380px wide with 18% of the map on screen; wrapping that into one shared grid fixed the width but left a dense fan of long crossing child links. Clustering keeps every child link short and local. Horizontal scroll stays at 1.0x at any device count; the cost is height (36 children ≈ 1700px). The column count is part of the render-cache signature, so a window resize re-flows rather than hitting the cache. The detail views label the **mesh-local** address alongside the OMR one: it is reachable only inside the mesh (a browser on the LAN has no route to that prefix) but, unlike RLOC16, survives roaming, so it is the stable handle for `ot-ctl ping` while RLOC16s churn. `meshLocalAddress` picks it by matching the overview's mesh-local prefix. Each node card carries a second small line with the measured link and how long ago the device was heard (`-68 dBm · 5s ago`), shown only where a link was actually measured — the local border router has no link to itself, and a bare "just now" there would say nothing. The card height lives in `TOPOLOGY_NODE_HEIGHT`, which the edge geometry and the cluster layout both read; it must match the CSS `min-height` or edges detach from the boxes. Cluster width is capped to fit two per band **only when the natural layout does not fit** — capping unconditionally wrapped three children onto two rows with room to spare. Selecting a map node opens `#devicePopover`, a fixed non-modal panel in the same family as the term-help and rename popovers (dismissed by its ×, Escape, an outside click, re-clicking the node, switching to List, or navigating away) — it replaced a docked inspector column so the map gets the full width.
- **Hiding elements**: use the `.hidden` class (`display: none !important`), never the bare `hidden` attribute. Several components set `display` in their own rules, which beats the UA stylesheet's `[hidden] { display: none }` — an element can carry `hidden` and still render.
- **`web/static/app.js`** — single-page vanilla JS; polls the internal API only, never OTBR directly. The CSP is `'self'`-only with no inline allowance, so no inline `<script>`/`<style>`/event handlers in `index.html`. Display names prefer `customName` (see `deviceLabel`); the rename popover is a fixed element outside the polled device containers so a background refresh can't clobber an in-progress edit.

- **`tools/matter-xref`** — a standalone Go command (not part of the server binary; `make build` only builds `./cmd/otbr-insight`) that matches Matter node IDs to mesh devices. A Matter QR code carries no Thread identity — only vendor/product IDs, a discriminator and the passcode — but the operational mDNS advert does: `_matter._tcp` instances are named `<compressed-fabric-id>-<node-id>` and their SRV target hostname **is the device's extended address**, which is exactly what this app keys devices on. Browsing mDNS has no stdlib support and every Go zeroconf library drags in `miekg/dns` (last release 2020, does not compile on Go 1.24 without forcing an `x/net` upgrade, ~+1.3 MB), so the tool shells out to `dns-sd` or `avahi-browse` instead. That is also why it is a tool and not a feature: the server itself stays REST-only, and (until the MCP SDK) dependency-free.

- **`internal/otctl`** — the OpenThread CLI over otbr-agent's POSIX daemon UNIX socket (`/run/openthread-wpan0.sock` by default, `--otbr-socket`), the same channel `ot-ctl` and otbr-web use. It exists for capabilities the REST API has no action for, and for replacing ones REST does badly. So far: **active network discovery**; the **live device inventory and topology** (`Mesh`); the **runtime status fields** (`Status`) that otbr-web served from `/get_properties` — version strings, channel, TX power, EUI-64, link-local and mesh-local addresses (the mesh-local EID via `ipaddr mleid` — a first-ULA scan of `ipaddr` is only a fallback, because the OMR address is a ULA too and on real hardware it is listed *before* the EID, which put the OMR address in the mesh-local field), cached for `statusTTL` since they are near-static, with `WPANService` *derived* from the role because the CLI has no direct equivalent; **reachability testing** (`Ping`), whose timeout must accommodate a sleepy device — measured replies take 2.5-5s and the CLI's one-second default reports a live device as 100% lost; and **event history** (`History`), OpenThread's own recorder, which is the only source for *when* something happened — REST reports current state only, so a departed device is simply absent with no record of when or at what signal. `Mesh` reads `meshdiag topology` for the router set and inter-router links, then `meshdiag childtable <rloc16>` per router — including our own, which works — for children with `ext-addr`, RSSI, margin and frame/message error rates. It answers from the mesh at the moment it is asked, so it has **no cache to go stale**: departed devices vanish at once and sleepy children need no sweep. `Mesh` splits its work by cost: the over-the-air `meshdiag` queries are cached for `meshStructureTTL` while ages and RSSI are re-read from the local `neighbor table` on every call, so "last seen" tracks reality without extra radio traffic. That is also why `Client.FastDevices` reports true when a live reader is present — `Monitor` then polls devices at the overview cadence instead of the 15s floor, which is what previously made "last seen" lag by up to a full interval. It is injected as an optional `otbr.MeshReader`, preferred by `Devices` and `Topology`, with one reading cached for `meshSnapshotTTL` (2s) so a poll queries each router once rather than twice. A failed read falls back to the REST collections and **logs the transition** (both directions) — otherwise the degradation is invisible in the API response. While the live reader works, `RefreshMesh` skips posting discovery actions entirely: they only refresh caches nothing reads, and each sweep costs airtime. **Error rates are a rolling EWMA, not a total.** `SuccessRateTracker::AddSample` computes `rate = (old*(n-1) + sample + n/2) / n` with the default weight `n = 64`, so the figure reflects roughly the last ~64 transmissions to that neighbour — it is neither "since attach" nor "since boot", and the wall-clock span it covers depends entirely on traffic. Also note the value comes from two different commands with different formatting: `meshdiag childtable` writes `30.97%` for children, `neighbor linkquality` writes `0.09 %` (with a space) and is the **only** source for a *router* neighbour's rates — children are all `meshdiag childtable` covers, which is why routers reported no retry data at all until it was added. Note `meshdiag` reports a dB link margin while the UI draws a 0–3 LQI, so `qualityFromMargin` maps it using OpenThread's own thresholds (>20 dB → 3, >10 → 2, >2 → 1). **Addresses need three sources.** `meshdiag childtable` carries no IPv6 at all, so children get theirs from `meshdiag childip6 <rloc16>`; routers appear in no childtable, so theirs come from `srp server host`, whose hostnames are extended addresses (`0102030405060708.default.service.arpa.`) and therefore join directly to how this app keys devices — skipping `deleted: true` entries, which are unexpired leases rather than live devices. The local border router registers nothing with its own SRP server, so its addresses come from `ipaddr` via `localAddresses`, which drops the link-local one and every `…:0:ff:fe00:xxxx` anycast/routing locator — those encode an RLOC16 or ALOC and churn with the node's role — leaving the mesh-local EID and the OMR address. Its OMR is also filled from the overview by `mergeBorderRouter` as a fallback. A child holds both a mesh-local and an OMR address and both are ULAs, so `pickOMR` classifies them against the prefix from `br omrprefix` rather than guessing by shape. One more live-data hazard: after roaming, **both the old and new parent list a child** until the stale entry ages out, so children are deduplicated by extended address. **Router link metrics come from elsewhere again**: `meshdiag topology` gives only an adjacency and its quality bucket, so `routerMetrics` reads `router table` (LQ in/out, path cost) and `neighbor table` (average and last RSSI) — both local, no radio cost — and applies them to router nodes and router links. A router's own row reads LQ 0 / cost 0 about itself, so the local router is excluded: rendering that would look like a dead link rather than "not applicable". Table parsing goes through `pipeTable`, which keys cells by header name; column sets vary by command and firmware, which is what made the missing `J` column in `discover` a non-event. otbr-web's `/available_network` is a JSON wrapper around the CLI scan table (`src/web/web-service/ot_client.cpp` dials the socket and `sscanf`s the output), and the REST `/api/actions` enum offers only `getEnergyScanTask`, an 802.15.4 energy-detect scan reporting RSSI per channel rather than the networks on air. `Execute` writes one command and reads until `Done`, turning `Error N: …` into a Go error and refusing a reply that never terminates; embedded newlines are rejected so a caller cannot smuggle a second command. **Discovery is probabilistic**: a pass sends one request per channel and listens briefly, and a neighbour's router answers after a random delay, so measured on live hardware a single `discover` heard a given neighbour in about half of runs (Nest 2/5, another 1/5) and the list changed on every press. `otbr.Client.ScanNetworks` therefore runs `networkScanPasses` (3) passes through `mergedDiscovery` and unions them by identity, reporting `Passes` so the UI can say so. Also measured: **the posix daemon holds one session at a time and a new connection displaces the old one mid-command** — a raw `discover` on a second connection received the header and then nothing, no rows and no `Done`, while the app polled, and completed once the app was stopped; the app's own commands are safe because `Execute` serialises them under one mutex, but a hand-run `ot-ctl discover` alongside the running app heard nothing in 4 of 5 runs. `ScanNetworks` prefers `discover` and falls back to `scan` on firmware without it — so this returns *more* than otbr-web did, whose results carried no name or extended PAN ID. **Verified against OPENTHREAD/8fbe09e**: `discover` emits seven columns — `Network Name | Extended PAN | PAN | MAC Address | Ch | dBm | LQI` — with **no joinable (`J`) column** despite the upstream CLI docs, CRLF line endings, and the *same network repeated once per responding beacon*, so exact duplicates are collapsed. The parser keys on the header row rather than column positions, which is why the missing `J` needed no change.

  It is wired in as an **optional** `otbr.NetworkScanner`, injected by `main` and preferred over the otbr-web endpoint when the socket exists; `internal/otbr` never imports it. A present-but-failing socket reports the failure rather than silently falling back, so the two sources stay distinguishable in the UI. **This is the one part of otbr-insight that must run on the border router** — a UNIX socket is not reachable over a network — so everything else stays REST-only and host-agnostic. Deployment: the socket is **mode 0755 root:root**, and since `connect()` needs write access **only root can open it** — measured, not assumed (a non-root process gets `connect: permission denied`). So `DynamicUser=yes` cannot scan; the unit documents running as root, granting a group, or accepting no scanning. It also needs `ReadWritePaths=-/run/openthread-wpan0.sock` under `ProtectSystem=strict`. Because `Available()` is only a stat, an unopenable socket would otherwise shadow a working otbr-web, so an error reporting `SocketUnavailable()` falls through to otbr-web while any other daemon error is surfaced — "could not reach the source" and "the source answered badly" are deliberately different. See `deploy/otbr-insight.service`.

A future `ot-ctl` provider is the intended extension point: implement `service.ThreadProvider` without touching `internal/model` or the frontend.

## Conventions

- Writes are **bounded and REST-only**, with one deliberate exception. The app talks to OTBR over the `:8081` REST API for everything it can, and never shells out to a binary. `internal/otctl` speaks the daemon socket protocol directly (no subprocess) **only** for active scanning, because REST has no action for it; it is optional and absent-socket means absent-capability. Do not widen it without a reason of the same kind: every capability added there costs the property that otbr-insight can run anywhere and point at any border router. PSKd commissioning and factory reset remain out of scope.
- **Never expose Thread credentials on a read path.** The network key and PSKc are masked in `ActiveDataset` and must stay masked; the frontend polls `/api/v1/network` continuously.
- Any new destructive/network-changing operation must go through the frontend confirm modal (`openConfirm`) — never fire it on a single click.
- Tests use `httptest` servers returning canned OTBR payloads (see `internal/otbr/client_test.go`); new normalization paths should get a fixture for each OTBR response variant they handle.
- **Sanitise fixtures at the point of capture, not at review.** Test payloads and the sample CLI output in doc comments are pasted from live hardware, so the moment to replace real values is when they are captured — by the time anything is being published it is already too late to be sure. This is not hypothetical: a pre-publication audit found the **live network key and PSKc** in `internal/otbr/network_test.go`, and that same key used as the `placeholder` on the Network key input in `index.html`, where it shipped inside the binary. Scrub credentials (network key, PSKc), network identity (name, PAN ID, extended PAN ID, mesh-local and OMR prefixes) and every hardware address — device extended addresses are effectively MACs, and so are the RCP's EUI-64 and the border-agent ID. Note also that a `discover` fixture captures **neighbouring networks**, whose names and extended PAN IDs are someone else's to publish rather than ours. Reuse the documentation values already in the tree (`00112233445566778899aabbccddeeff`, `1122334455667788`, `fdde:ad00:beef`, `fd11:2233:4455`, sequential `0102030405060708`-style addresses), keeping the same length and shape so header-keyed table parsing and prefix matching still exercise what they did. Two traps that a search for the full secret will miss: a PAN ID also appears in **decimal** (`0xa1b2` is `41394`), and an assertion may check an **8-character prefix** of a key rather than the whole value.
- Topology child nodes are identified by **extended address** whenever the diagnostic `children` TLV (TLV 30) reports one: `childTable` carries only a child ID, but `children` adds `extAddress` and the real `rloc16`, so `decodeTopology` merges the two by child ID. That extended address is what matches the device inventory, so user-assigned names reach the map and a child can be renamed from it. Firmware that omits `children` falls back to the old derived id (`<parent>/child/<n>`, RLOC16 computed as parent+childID), which is stable only within one topology snapshot — keep that fallback working.
